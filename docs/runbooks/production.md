# Production deployment prerequisites

Local Compose deliberately forces `MODE=development` and publishes loopback ports. Do not expose it on a public interface. Prepare a separate production deployment using a TLS reverse proxy, private PostgreSQL/artifact network, secrets manager, allowed host list, secure cookies and an OIDC issuer/client registration. Supply MODE=production, high-entropy SESSION_SECRET, OIDC_ISSUER, OIDC_CLIENT_ID and OIDC_CLIENT_SECRET. Register the exact HTTPS callback URI documented by the application and configure provider/LLM budgets and dated pricing. Browser clients never receive provider/client secrets.

Production must fail closed when OIDC or session/budget configuration is missing. Test that development login is unavailable in production, expired/mismatched identity tokens are rejected, membership is enforced, cross-workspace resources return indistinguishable 404, and CSRF protects cookie mutations. Server-side OIDC exchange and issuer/audience validation are required; merely setting these variables does not establish verified authentication. No production OIDC tenant or TLS deployment has been verified here.

Use a dedicated database application role with minimum privileges. Run Alembic as a deployment migration job before API/worker rollout. Run nonroot image with read-only root filesystem and writable private `/data`, restrict memory/process resources, redact content-free logs, and limit concurrency/provider spending. Do not horizontally scale workers before testing lease fencing against PostgreSQL. There is no Redis or S3 dependency in this authorized local architecture; shared local volumes constrain multi-host scaling and require a deliberate future storage adapter.

Configure backups, independent deletion-ledger durability, source/log/grace retention and restore drills before storing newsroom data. Readiness, latency, budgets, failed acquisition reasons and unknown invocation charges need operational alerts. CI publishes nothing. Provider account permissions, public release, licensing, contest submission and meaningful spend require separate user authority.

## Database roles and maintenance

The PostgreSQL migration creates `evidence_app` as NOLOGIN/NOSUPERUSER/NOBYPASSRLS and grants application-table access. Provision a separate private LOGIN role without ownership or BYPASSRLS, grant it membership in evidence_app, and use that login in runtime DATABASE_URL. Do not use the local Compose `evidence` owner in production. Tenant tables require the transaction-local `app.workspace_id`; missing scope returns no rows and rejects writes. Identity bootstrap tables (`users`, `memberships`, `workspaces`) rely on API authorization because membership lookup precedes workspace selection; no complete database-wide isolation claim is made.

Use a separate privileged migration/maintenance identity for Alembic, backup restore, `scripts/reapply_deletions.py` and `scripts/cleanup_retention.py`; do not place its credentials in API/worker environments. Maintenance operates across workspaces. Schedule `python /app/scripts/cleanup_retention.py` for dry-run reports and add `--apply` only for the configured policy. After a deleted-case purge, retained Case tombstones have `state=PURGED` and must not be restorable. Provider artifacts, original claims, snapshots and exports for that case are removed. Raw-source expiry on active cases retains immutable quotation/review/export envelopes and original hashes but marks source storage EXPIRED.

## Initial OIDC membership

OIDC login does not grant itself workspace membership. A privileged administrator must verify the account in the configured identity provider, obtain its exact `iss` and `sub` values, and provision that identity locally with `python /app/scripts/bootstrap_oidc.py --issuer 'https://id.example/issuer' --subject 'verified-account-sub' --display-name 'Editor' --workspace-id 'workspace-uuid' --workspace-name 'Newsroom' --role owner`. Use the separate maintenance DATABASE_URL, never API runtime credentials. This computes the same SHA256(issuer + '|' + subject) user id as login; exact issuer spelling, including a trailing slash, must match the provider claim. The CLI validates input shape and database maintenance privilege; it cannot independently establish that the supplied account belongs to a person. The administrator performs that verification. It creates only absent workspace/user/membership rows and refuses to overwrite an existing role. Add a distinct editor/researcher for review separation. Set OIDC_WORKSPACE_ID to the provisioned workspace id and PUBLIC_URL to the HTTPS origin before login; the callback is `/v1/auth/callback`. No subject, provider secret or credential is printed.
